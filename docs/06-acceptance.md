# 구현 순서와 검증 게이트

이 문서는 세로 구현 순서와 완료 판정의 유일한 기준이다. 각 단계는 해당 결과가 화면, API, DB 또는 명령으로 확인된 뒤 다음 단계로 넘어간다.

## 단계 1. 골격과 계약

React/Vite/shadcn, FastAPI, PostgreSQL Compose, 마이그레이션, 환경설정과 health를 만든다. 요청·응답 DTO와 상태 enum을 테스트로 고정한다.

완료: 프런트엔드, API와 DB가 로컬에서 실행되고 migration, API 테스트, liveness와 readiness가 통과한다.

## 단계 2. 인증과 기업정보

관리자 CLI 사용자 생성, session cookie, CSRF, 보호 라우트, 기업정보 입력·검증·버전을 구현한다.

완료: 새 사용자가 로그인하고 기업명만으로 저장할 수 있으며 잘못된 값은 UI와 API에서 거부되고 불변 스냅샷이 생성된다.

## 단계 3. 공고 한 건 수집

기업마당 한 건을 운영 parser 또는 동일 형식 fixture로 가져와 공고버전, 원문, 첨부 메타데이터와 허용 원본을 저장한다.

완료: DB에서 저장 원본까지 역추적되고 해시가 일치하며 같은 입력 재수집은 중복 버전을 만들지 않는다.

## 단계 4. 공고 한 건 분석

네이티브 추출, 조건부 OCR, 조건 JSON Schema, 근거 검증과 단계 기록을 구현한다.

완료: 실제 공고 한 건의 모든 공개 조건에 저장된 원문 근거가 있고, 실패·입력 잘림·누락 경로가 NEEDS_CONFIRMATION으로 귀결된다.

## 단계 5. 결정론 판정

날짜·수치·enum·지역 규칙과 3단계 집계를 먼저 구현하고 자유 업종, 중복수혜와 모호 문장의 AI 의미판단을 연결한다.

완료: PASS·UNKNOWN·FAIL, 복수 유형, 역할, 완화 가정, 지역·단위 오판 회귀 테스트가 통과한다.

## 단계 6. 목록과 상세 세로 경로

서버 페이지네이션, 필터, 공용 상세 모달, 원문 근거, 첨부 열기, 관심 상태, 역할·답변과 기업정보 변경 재판정을 연결한다.

완료: 로그인부터 기업정보 저장, 판정 카드, 상세 근거와 관심 선택까지 데스크톱과 모바일에서 한 흐름으로 동작한다.

## 단계 7. 운영 확장

증분 수집, 주간 대조, 누락 실행, 작업 큐, 재시도, CLI 상태·재분석과 안전한 worker 종료를 구현한다.

완료: 일부 job 실패가 다른 job을 롤백하지 않고, 재시도·재분석이 지정 대상에만 적용되며 중단된 자식 프로세스가 결과를 commit하지 않는다.

## 단계 8. 외부 배포

Vercel, FastAPI, PostgreSQL, worker, Cloudflare Tunnel과 Access를 연결한다.

완료: 실제 배포 URL에서 로그인, 기업정보, 목록, 상세 근거와 첨부 다운로드가 동작하고 공개·보호 health 접근 테스트가 통과한다.

## 도메인 테스트

- FAIL 하나와 UNKNOWN 여러 개가 함께 있어도 INELIGIBLE
- FAIL 없이 UNKNOWN이 있으면 NEEDS_CONFIRMATION
- 적용 필수조건이 모두 PASS일 때만 ELIGIBLE
- 우대·이행·증빙 조건은 판정을 바꾸지 않음
- 복수 유형 중 한 유형 전체 통과 시 ELIGIBLE
- 역할 미선택은 NEEDS_CONFIRMATION이고 선택 후 해당 역할만 재판정
- 체납 제한이 없는 공고에서 체납 있음이 자동 FAIL을 만들지 않음
- 승인된 매출·인원 대체값에 assumption code가 남음
- 원문에 없는 조건을 생성하거나 공개하지 않음
- 명확한 지역 불일치는 INELIGIBLE, 변환 실패·동명 지역은 NEEDS_CONFIRMATION
- `전국`과 `국내`를 특정 지역 제한으로 추출하지 않음
- 숫자의 대상·단위·연산자·기업정보 필드가 다르면 자동 비교하지 않음
- Asia/Seoul 기준으로 마감 당일을 포함함

## 파일과 AI 테스트

- 같은 해시 재수집은 새 버전과 분석을 만들지 않음
- 최신 정정 공고가 본문·안내서·기타 첨부보다 우선함
- 다운로드 상태와 추출 상태가 독립적으로 전이함
- 20MB 파일·100MB 공고·ZIP 200항목 제한과 traversal 방어
- PDF·이미지 페이지와 Office 파일명 근거가 보존됨
- PDF 일부 네이티브 텍스트가 있으면 추가 OCR하지 않는 승인 정책
- 180,000자 초과 입력에 `ATTACHMENT_INPUT_TRUNCATED`와 NEEDS_CONFIRMATION
- 모델과 effort가 단계 계약과 정확히 일치하고 사용자 전역 설정을 상속하지 않음
- 모델을 사용할 수 없을 때 다른 모델로 fallback하지 않음
- 첨부의 프롬프트 인젝션 문구가 명령·도구 실행을 만들지 않음
- 설명 모델이 calculated verdict를 바꾸지 못함
- 설명 실패 시 계산값을 보존하고 공개 판정만 NEEDS_CONFIRMATION으로 바뀜
- 동시 5개 job이 독립 session·transaction으로 처리됨
- lease 상실 또는 worker 종료 뒤 Codex 자식이 commit하지 못함

## API와 보안 테스트

- GET 전용 필드와 폐기한 이전 필드를 PUT에 보내면 422
- 기업정보 If-Match 충돌과 오래된 공고버전 변경 요청은 409
- 같은 역할·답변·재판정 요청이 중복 job을 만들지 않음
- 다른 origin에서 credential CORS와 CSRF가 계약대로 동작함
- 비인증 사용자가 앱 API와 첨부에 접근하지 못함
- 다른 사용자의 자원은 404로 존재가 숨겨짐
- session token 원문과 기업정보 원문이 일반 로그에 남지 않음
- 세션 만료 뒤 로그인하면 원래 상세 URL로 복귀함
- public liveness가 내부 상태를 노출하지 않고 readiness는 Access로 보호됨

## UI 테스트

- API가 고정한 페이지 크기의 전체 건수, 필터와 정렬이 일치함
- 기간 미확인 공고가 마감일 정렬 뒤쪽에 위치함
- 모달 URL, 뒤로가기, 직접 URL 진입과 목록 scroll 복원
- 전체 공고와 관심 공고가 같은 상세 컴포넌트를 사용함
- 상세 조건 전체와 원문 근거가 표시됨
- 본문만 스크롤되고 관심 버튼 3개가 데스크톱·모바일에서 동일 너비로 고정됨
- 로딩·조회 실패 중 하단 관심 버튼이 나타나지 않음
- 대기·실행 공고가 숨겨지고 최종 실패는 확인 필요로 표시됨
- 빈 데이터와 빈 필터 결과, 404가 서로 다른 안내를 제공함
- 기업정보 오류는 입력 중 표시되고 저장을 막지만 정상 상태 제한 카운터는 숨김
- 키보드만으로 로그인, 목록, 모달, 필터와 폼을 사용할 수 있음

## 지역 데이터와 fixture

- canonical 지역 원본의 provenance SHA-256이 실제 파일과 일치함
- 백엔드와 프런트 배포 사본이 canonical 원본과 byte-for-byte 일치함
- 시·도 부모 포함, 시·군·구 정확 비교, 안전한 약칭과 동명 지역 거부 테스트
- 기업마당 fixture가 운영 parser를 통과하고 원본 wrapper를 보존함
- 네이티브 HWPX/PDF, 혼합 PDF, Vision OCR과 한도 초과 fixture를 포함함
- fixture manifest에 입력·원본 해시, 기대 canonical IR, 근거 위치와 예상 AI 단계가 있음

## 홀드아웃 품질 게이트

튜닝에 사용한 기업·공고 쌍과 최종 검증 쌍을 분리한다. 홀드아웃은 최소 5쌍이며 명시적 탈락과 알려진 신청 가능 사례를 모두 포함한다. 기대 판정은 파이프라인과 프롬프트를 보지 않은 사람이 공식 원문 근거로 먼저 작성하고 manifest 해시와 함께 동결한다. 기대값은 모델 입력에 넣지 않는다.

가능하면 규칙·프롬프트 작성자가 아닌 두 번째 사람이 확인한다. 한 명이면 정답 작성과 시스템 실행을 시간적으로 분리하고 그 한계를 보고한다.

통과 조건은 알려진 신청 가능 사례를 모두 찾고 명시적 탈락 사례를 ELIGIBLE로 내는 건수가 0인 것이다. 표본이 5쌍보다 적으면 통과로 선언하지 않는다. 실제 신청 가능을 놓친 수와 명시적 탈락을 신청 가능으로 낸 수를 따로 보고한다.
